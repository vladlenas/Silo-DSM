# Silo DSM

Synology DSM 7 package for **TorrServer Silo**, the from-scratch rewrite of
TorrServer on the [`silo` branch](https://github.com/YouROK/TorrServer/tree/silo).

> **Early development.** Upstream describes Silo as a sketch where things do
> not work yet, and everything (API, configuration, layout) will change. This
> package is published as **beta** only. For daily use, take
> [TorrServer DSM](https://github.com/vladlenas/TorrServer-DSM).

The package is built the same way as TorrServer DSM (same scripts, Helper and
release workflow) and is meant to run **next to it**:

| | TorrServer DSM | Silo DSM |
|---|---|---|
| DSM package name / user | `TorrServer` | `TorrServerSilo` |
| Web port | 8090 | **8095** |
| Helper (settings window) | 127.0.0.1:42777 | 127.0.0.1:**42778** |
| Data | `/var/packages/TorrServer/var` | `/var/packages/TorrServerSilo/var` |
| Log | `TorrServer.log` | `Silo.log` |

## Features

- Silo compiled from a **pinned commit** of the `silo` branch; packages are
  released for **amd64** only (Intel/AMD models)
- `config.yaml` is generated by the package from the install wizard and the
  Helper (port, data folder, log level, owner password, transcoding)
- Transcoding with **FFmpeg 7 from SynoCommunity**, installed as a dependency
- **VAAPI** on Intel models: the package asks DSM for GPU access, and the
  Helper has a **Test VAAPI** button
- Works with Silo's own **WebDAV plugin**: the torrent library as a network
  folder for players such as **ViMu** (no FUSE needed), see [WebDAV for ViMu](#webdav-for-vimu)
- Helper in English, Russian, Ukrainian, Lithuanian and Polish; logs and status
- Runs as its own unprivileged DSM user; nothing runs as root

## Requirements

- Synology DSM 7.3 or newer
- The **SynoCommunity** package source in Package Center
  (`https://packages.synocommunity.com/`): DSM installs **FFmpeg 7** from it
  before Silo DSM. Without the source the installation stops and says the
  dependency is missing.
- Python 3.7 or newer (DSM 7 includes it)
- A DSM administrator account to open the Helper

## Installation

DSM 7 hides packages marked `beta="yes"` in the normal Package Center
channel, so Silo DSM is distributed through SSpkS:

1. Package Center → Settings → Package Sources: add the SynoCommunity source
   and the SSpkS server that publishes Silo DSM.
2. Install **TorrServer Silo**. The wizard asks for the web port (8095), an
   optional owner password and the transcoding mode (CPU, VAAPI or automatic).
3. Open **TorrServer Silo** from the DSM main menu. Silo's own web page is at
   `http://<NAS address>:8095`.

Manual install of a `.spk` from the
[Releases](https://github.com/vladlenas/Silo-DSM/releases) page works too
(FFmpeg 7 must then be installed first).

## How the configuration works

Silo reads everything from one file: `silo -c config.yaml`. The package keeps
its own settings in `/var/packages/TorrServerSilo/var/settings.json` and
**generates `config.yaml` from it**:

- after installation, from the wizard answers,
- before every start of Silo,
- when settings are saved in the Helper.

So `config.yaml` is never edited by hand; use the Helper. Settings that the
package does not manage are left out of the file, and Silo uses its own
defaults for them. Logging goes to Silo's stdout, which the package writes to
`Silo.log` (rotated by the Helper at 2 MB).

The owner password is stored in `settings.json` and `config.yaml`, both readable
only by the `TorrServerSilo` user (mode 600).

**The torrent engine is not set here.** Cache (RAM or disk), its size, peers
and speed limits are set in Silo's own web interface (Settings); Silo keeps
them in its database and does not read them from `config.yaml`. Silo runs in
`/var/packages/TorrServerSilo/var`, so a relative disk-cache folder (Silo's
default is `torrents`) ends up there.

## Data folder

By default Silo keeps its database and transcoding cache in
`/var/packages/TorrServerSilo/var/data`. To keep them on a shared folder:

1. Control Panel → Shared Folder → Edit → Permissions → System internal user:
   give **TorrServerSilo** Read/Write.
2. Helper → Settings → **Data folder** → Browse, then Save and Restart.

Existing data is not moved when the folder changes. The install wizard does
not ask for a folder: the package user does not exist before installation, so
it could not have the permission yet.

## Transcoding and VAAPI

Silo looks for a binary called `ffmpeg` (and `ffprobe` next to it) in `PATH`.
The package puts `/var/packages/ffmpeg7/target/bin` first in Silo's `PATH`;
SynoCommunity's FFmpeg 7 has `ffmpeg` and `ffprobe` there (`ffmpeg7` and
`ffprobe7` are links to them).

Hardware acceleration on Intel models goes through VAAPI and `/dev/dri`:

- `conf/resource` requests `"video-driver"`, the DSM resource that gives a
  package user access to the GPU (the same one SynoCommunity packages use).
- FFmpeg 7 pulls in **synocli-videodriver**, which brings the Intel VAAPI
  drivers.
- The Helper **Status** page shows the FFmpeg version, whether this FFmpeg
  build supports VAAPI, every `/dev/dri/renderD*` node with its group and
  whether the package user can open it, and the user's groups.
- **Test VAAPI** runs two checks as the package user, i.e. with exactly the
  rights Silo has: the device probe Silo itself runs before choosing VAAPI,
  and a one-second H.264 encode with `h264_vaapi`.

If the test fails with a permission error, the package user is not in the
group that owns `/dev/dri/renderD128` (usually `videodriver`): reinstall the
package so DSM applies the `video-driver` resource, then check again. ARM
models have no VAAPI; use CPU transcoding there.

## WebDAV for ViMu

Silo has no FUSE. Its plugin store has a **WebDAV** plugin
([TorrServer-Project/plugin-webdav](https://github.com/TorrServer-Project/plugin-webdav))
that shares the torrent library read only: categories, torrents, their folders
and files, with seeking (HTTP Range).

1. Silo (`http://<NAS address>:8095`) → admin panel → **Plugins** → Store →
   install **WebDAV**.
2. Open the plugin page (`http://<NAS address>:8095/plugins/webdav/`) and set a
   **WebDAV password** (at least 4 characters). The plugin always asks for a
   login, also when Silo itself has no owner password, and it uses this
   password, not Silo's.
3. In ViMu add a **WebDAV** network source:
   - address (`dav://` field): `<NAS address>:8095/plugins/webdav/dav/`
   - user: your Silo user name (`owner` when Silo has no password)
   - password: the WebDAV password from step 2
4. Torrents appear once Silo has their file list (metadata).

## Troubleshooting

- **Silo does not start:** Helper → Logs, `Silo.log`. The status page also
  shows the last lines of the log while Silo is stopped.
- **Port already in use:** another program uses 8095; change the port in the
  Helper.
- **"FFmpeg 7 was not found"** in the log: install FFmpeg 7 from SynoCommunity.
  Silo still runs, without transcoding.

## Development

### Building

```sh
make            # spk/Silo-DSM-<version>-amd64.spk
make silo-amd64 # the same, by architecture
make binaries   # only the Silo binary (dest_bin/<commit>/)
make clean
```

Needs Go 1.26 or newer (or a Go that may download it, `GOTOOLCHAIN=auto`), git
and xz. `build-package.sh` fetches exactly the pinned commit (shallow), checks
that the checkout is that commit, and compiles with the flags of upstream
`build-all.sh` (`CGO_ENABLED=0`, `-tags=nosqlite`, `-checklinkname=0`):

Only `amd64` is released (`ARCHES` in `Makefile`). `build-package.sh` still
knows `arm64` and `arm7` (`GOARCH=arm GOARM=7`): `make silo-arm64` builds one
by hand.

`SILO_PREBUILT_DIR=<dir>` packages ready binaries (`silo-linux-<arch>`)
instead of compiling them.

### Versions and releases

`Makefile` pins the upstream code:

```make
SILO_VERSION := Silo.1
SILO_COMMIT := fc5795e10234d18dda509a781472a82e402322bd
PKG_VERSION := 0.1.1
```

`SILO_COMMIT` is a full commit id, so the pin cannot move like a branch or a
tag. The last number of `PKG_VERSION` is the Silo build (`Silo.1` → `x.y.1`).

To release: update the three values, add a `CHANGELOG.md` entry for the new
`PKG_VERSION` and merge to `main`. The **Build** workflow runs the tests, builds
the amd64 package with Go 1.26, and publishes a GitHub **pre-release**
`v<PKG_VERSION>` with the `.spk` and `SHA256SUMS`. Every package
carries `beta="yes"`.

### Tests

```sh
python3 -m unittest discover -s tests -v   # config.yaml generator and Helper
sh tests/test_scripts.sh                   # start, stop, restart, postinst with a fake Silo

```
